# งาน: ระบบบีบอัดรูปและไฟล์สำหรับทุกการอัปโหลดในเว็บ

อ่านเอกสารนี้ให้จบทั้งหมดก่อนเริ่มทำงาน แล้วทำตามขั้นตอนตามลำดับ

---

## 1. บริบทและเป้าหมาย

- เว็บนี้ยังพัฒนาไม่เสร็จ มีหลายโมดูลที่ให้ผู้ใช้อัปโหลดรูปและไฟล์ และจะมีโมดูลใหม่เพิ่มอีกในอนาคต
- ข้อมูลทั้งหมดต้องเก็บไว้อย่างน้อย **10 ปี**
- เซิร์ฟเวอร์ตอนนี้มีดิสก์ 40GB ใช้ไปแล้ว 9.9GB เหลือว่างประมาณ 28GB และระบบรันอยู่บน Docker
- รูปจากมือถือมีขนาดประมาณ 3–5MB ต่อรูป ถ้าไม่บีบอัด พื้นที่จะเต็มภายในไม่กี่ปี

**เป้าหมาย:** ทุกไฟล์ที่เข้ามาในระบบต้องถูกบีบอัดให้เล็กที่สุด แต่ยังอ่านได้ชัดและใช้งานได้ตามปกติ โดยทำผ่านจุดเดียวที่ทุกโมดูลใช้ร่วมกัน

## 2. ขอบเขต

งานนี้ครอบคลุม **ทุกการอัปโหลดในเว็บ** ไม่จำกัดเฉพาะเอกสารประเภทใดประเภทหนึ่ง ได้แก่
- เอกสารทุกประเภท เช่น ใบขอซื้อ ใบสั่งซื้อ ใบเสนอราคา ใบแจ้งหนี้ ใบเสร็จ สัญญา และอื่นๆ
- ไฟล์แนบทุกชนิดในทุกฟอร์ม
- รูปโปรไฟล์ โลโก้ รูปสินค้า และรูปอื่นๆ ทั้งหมด
- ทุกโมดูลที่มีอยู่แล้ว และทุกโมดูลที่จะสร้างในอนาคต

## 3. ขั้นตอนการทำงาน

### ขั้นที่ 1: สำรวจโปรเจกต์ (ห้ามแก้โค้ดในขั้นนี้)

1. ระบุภาษา framework ฐานข้อมูล และโครงสร้างโปรเจกต์
2. หาทุกจุดที่รับไฟล์จากผู้ใช้ ทั้ง backend (route, controller, API) และ frontend (input type="file", drag & drop, การวางรูป)
3. ดูว่าตอนนี้ไฟล์ถูกเก็บที่ไหน (ดิสก์ในเครื่อง, Docker volume หรือ cloud) และในฐานข้อมูลเก็บข้อมูลไฟล์อย่างไร
4. ตรวจ Dockerfile และ docker-compose เพื่อดูว่าไฟล์ที่อัปโหลดอยู่ใน volume ที่คงอยู่หรือไม่ (ถ้าไม่อยู่ ไฟล์จะหายเมื่อ rebuild container ให้แจ้งฉันทันที)
5. นับจำนวนและขนาดรวมของไฟล์ที่อัปโหลดไว้แล้ว (ถ้ามี)

**รายงานให้ฉันเป็นตาราง:** จุดอัปโหลด | ไฟล์/path | ชนิดไฟล์ที่รับ | ที่เก็บ | จำกัดขนาดหรือยัง

### ขั้นที่ 2: เสนอแผน (รอฉันอนุมัติก่อนเขียนโค้ด)

สรุปให้ฉันดูว่า
- จะสร้าง upload service กลางไว้ที่ไหน ตั้งชื่ออะไร
- จะใช้ library และเครื่องมืออะไร และต้องติดตั้งอะไรเพิ่มใน Dockerfile
- จะแก้จุดอัปโหลดเดิมจุดไหนบ้าง
- จะเพิ่มหรือแก้ตารางในฐานข้อมูลอย่างไร
- มีความเสี่ยงหรือข้อที่ต้องตัดสินใจอะไรบ้าง

### ขั้นที่ 3: สร้าง upload service กลาง

สร้าง service/module เดียวที่ทำหน้าที่ทั้งหมดตามลำดับนี้

```
รับไฟล์
  → ตรวจขนาดไฟล์ (เกินกำหนด = ปฏิเสธ)
  → ตรวจชนิดไฟล์จากเนื้อไฟล์จริง (ไม่อยู่ใน whitelist = ปฏิเสธ)
  → บีบอัดตามชนิดไฟล์ (ดูหัวข้อ 4)
  → ตั้งชื่อใหม่เป็น UUID
  → บันทึกลง storage
  → บันทึกข้อมูลไฟล์ลงฐานข้อมูล
  → คืนค่าข้อมูลไฟล์ให้ผู้เรียก
```

ทุกโมดูลต้องเรียกใช้ service นี้เท่านั้น ห้ามมีโค้ดบันทึกไฟล์กระจายอยู่ในแต่ละหน้า

### ขั้นที่ 4: แก้ทุกจุดอัปโหลดเดิมให้มาใช้ service กลาง

แก้ทุกจุดที่พบในขั้นที่ 1 และลบโค้ดบันทึกไฟล์แบบเดิมออก

### ขั้นที่ 5: ปรับหน้าเว็บ (frontend)

- ตั้งค่า `accept` ใน input ให้ตรงกับ whitelist
- ตรวจขนาดไฟล์ก่อนส่ง ถ้าเกินกำหนดให้แจ้งทันทีโดยไม่ต้องรออัปโหลดเสร็จ
- ย่อรูปฝั่ง browser ก่อนส่งด้วยก็ได้ เพื่อให้อัปโหลดเร็วขึ้น (ไม่บังคับ เพราะ server ต้องบีบอัดอีกรอบอยู่แล้ว)
- แสดงสถานะระหว่างอัปโหลดและประมวลผล
- ข้อความ error ต้องเป็นภาษาไทยที่ผู้ใช้เข้าใจ เช่น "ไฟล์ใหญ่เกิน 20MB" หรือ "ไม่รองรับไฟล์ชนิดนี้ รองรับเฉพาะ JPG, PNG, PDF, Word, Excel"

## 4. สเปกการบีบอัดแยกตามชนิดไฟล์

### 4.1 รูปภาพ (JPG, JPEG, PNG, WEBP, HEIC, HEIF, GIF ที่ไม่เคลื่อนไหว)

ทำตามลำดับนี้
1. **หมุนรูปให้ถูกทิศตาม EXIF ก่อน** (ถ้าลบ EXIF ก่อนหมุน รูปจากมือถือจะเอียงหรือกลับหัว)
2. **ลบ metadata ทั้งหมด** ทั้ง EXIF, GPS และข้อมูลกล้อง เพื่อลดขนาดและปกป้องความเป็นส่วนตัว
3. **ย่อขนาด** ให้ด้านที่ยาวที่สุดไม่เกิน **2000px** รักษาสัดส่วนเดิม และห้ามขยายรูปที่เล็กกว่านี้
4. **แปลงเป็น WebP ที่ quality 80**
5. ถ้ารูปมีพื้นหลังโปร่งใส (PNG) ต้องคงความโปร่งใสไว้
6. ถ้าไฟล์ที่บีบแล้วใหญ่กว่าไฟล์เดิม (เกิดได้กับรูปเล็กมาก) ให้เก็บไฟล์ที่เล็กกว่า

**ข้อควรระวัง:** รูปถ่ายเอกสารต้องยังอ่านตัวหนังสือได้ชัดเจน ห้ามลด quality ต่ำกว่า 75 หรือย่อต่ำกว่า 1600px สำหรับรูปเอกสาร

**รูปย่อ (thumbnail):** สร้างรูปย่อด้านยาว 400px แบบ WebP quality 70 สำหรับหน้าแสดงรายการ เพื่อไม่ต้องโหลดรูปเต็ม (รูปละประมาณ 20–40KB)

**ไม่เก็บไฟล์ต้นฉบับ** เก็บเฉพาะไฟล์ที่บีบอัดแล้วและรูปย่อ

### 4.2 PDF

1. บีบอัดด้วย **Ghostscript** โดยใช้การตั้งค่าที่ลดความละเอียดรูปในไฟล์ให้เหลือประมาณ **150 dpi** (ใกล้เคียง preset `/ebook`)
2. เปรียบเทียบขนาดไฟล์ ถ้าไฟล์ที่บีบแล้ว**ไม่เล็กลงอย่างน้อย 10%** ให้เก็บไฟล์เดิม (PDF ที่เป็นข้อความล้วนมักบีบไม่ลง)
3. ถ้าบีบอัดล้มเหลว หรือใช้เวลานานเกิน 60 วินาที ให้เก็บไฟล์เดิม เขียน log และ**ห้ามทำให้การอัปโหลดล้มเหลว**
4. PDF ที่มีรหัสผ่านหรือเสียหาย ให้เก็บไฟล์เดิมโดยไม่บีบอัด และเขียน log ไว้
5. ต้องเพิ่ม Ghostscript ลงใน Dockerfile

### 4.3 ไฟล์ Office (DOCX, XLSX, PPTX)

- ไฟล์เหล่านี้เป็น zip ที่บีบอัดมาในตัวอยู่แล้ว **ไม่ต้องบีบซ้ำ** เพราะแทบไม่ได้ผลและเสี่ยงทำไฟล์เสีย
- ใช้วิธีจำกัดขนาดไฟล์แทน

### 4.4 ไฟล์ Office แบบเก่า (DOC, XLS, PPT)

- ไม่รับเป็นค่าเริ่มต้น เพราะเสี่ยงเรื่องความปลอดภัย (macro) ถ้าจำเป็นต้องรับ ให้ถามฉันก่อน

### 4.5 ไฟล์ข้อความ (TXT, CSV)

- เก็บตามเดิม และจำกัดขนาดไฟล์

### 4.6 ไฟล์ที่ไม่รับ

- ไฟล์ที่รันได้ทุกชนิด (exe, bat, sh, js, php ฯลฯ), zip/rar, วิดีโอ และเสียง
- ถ้าโมดูลไหนจำเป็นต้องรับไฟล์เหล่านี้ ให้ถามฉันก่อน

## 5. ค่าตั้งต้น (ต้องปรับได้จาก config หรือ environment variable ไม่ hardcode)

| ค่า | ค่าเริ่มต้น |
|---|---|
| ขนาดไฟล์สูงสุดต่อไฟล์ (ก่อนบีบอัด) | 20MB |
| จำนวนไฟล์สูงสุดต่อการอัปโหลดหนึ่งครั้ง | 10 ไฟล์ |
| ด้านยาวสูงสุดของรูป | 2000px |
| quality ของ WebP | 80 |
| ด้านยาวของรูปย่อ | 400px |
| quality ของรูปย่อ | 70 |
| dpi ของรูปใน PDF | 150 |
| เวลาสูงสุดในการบีบอัดหนึ่งไฟล์ | 60 วินาที |
| ชนิดไฟล์ที่อนุญาต | jpg, jpeg, png, webp, heic, heif, gif, pdf, docx, xlsx, pptx, txt, csv |

แต่ละโมดูลกำหนด whitelist ให้แคบกว่าค่ากลางได้ เช่น รูปโปรไฟล์รับเฉพาะรูป แต่ห้ามกว้างกว่าค่ากลาง

## 6. ความปลอดภัย

- **ตรวจชนิดไฟล์จากเนื้อไฟล์จริง (magic bytes)** ห้ามเชื่อนามสกุลหรือ Content-Type ที่ browser ส่งมา
- **ตั้งชื่อไฟล์ใหม่เป็น UUID** และห้ามใช้ชื่อไฟล์จากผู้ใช้เป็น path (ป้องกัน path traversal)
- เก็บชื่อไฟล์เดิมไว้ในฐานข้อมูลเพื่อแสดงผลและใช้ตอนดาวน์โหลดเท่านั้น
- ห้ามเก็บไฟล์ที่อัปโหลดไว้ในโฟลเดอร์ที่ server รันโค้ดได้
- ไฟล์ของเอกสารภายในต้องดาวน์โหลดผ่าน route ที่ตรวจสิทธิ์ผู้ใช้ ห้ามเปิดเป็นลิงก์สาธารณะที่ใครก็เข้าได้
- ตอนดาวน์โหลด ตั้ง header `Content-Disposition` ให้ถูกต้อง และตั้ง `X-Content-Type-Options: nosniff`

## 7. ฐานข้อมูลและ storage

### 7.1 ข้อมูลไฟล์ที่ต้องบันทึก

ใช้ตารางกลางตารางเดียว เช่น `files` หรือ `attachments` ให้ทุกโมดูลอ้างอิงถึง โดยมีข้อมูลอย่างน้อย
- id
- ชื่อไฟล์เดิม (สำหรับแสดงผล)
- path หรือ key ใน storage
- path ของรูปย่อ (ถ้ามี)
- MIME type หลังบีบอัด
- ขนาดก่อนบีบอัด (bytes)
- ขนาดหลังบีบอัด (bytes)
- สถานะการบีบอัด เช่น compressed, skipped หรือ failed
- ผู้อัปโหลด
- วันเวลาที่อัปโหลด
- โมดูลและรายการที่ไฟล์นี้เป็นของ

### 7.2 storage

- ออกแบบ storage เป็น interface (เช่น save, get, delete, getUrl)
- ตอนนี้ใช้ดิสก์ในเครื่องผ่าน Docker volume ที่คงอยู่
- ต้องสลับไปใช้ object storage (S3, Cloudflare R2, DigitalOcean Spaces) ได้ในภายหลัง โดยเปลี่ยนแค่ config ไม่ต้องแก้โค้ดในโมดูลต่างๆ
- แยกโฟลเดอร์ตามปีและเดือน เช่น `uploads/2026/09/uuid.webp` เพื่อให้จัดการและสำรองข้อมูลได้ง่าย

### 7.3 การลบไฟล์

- เมื่อลบรายการที่มีไฟล์แนบ ต้องลบไฟล์จริงและรูปย่อออกจาก storage ด้วย ไม่ให้เหลือไฟล์ขยะ
- ถ้าระบบใช้ soft delete ให้ถามฉันก่อนว่าจะจัดการไฟล์อย่างไร

## 8. การทดสอบ

เขียน test ให้ครอบคลุมกรณีเหล่านี้
- รูป JPG จากมือถือขนาดใหญ่ (4000px ขึ้นไป, 3–5MB) → ต้องถูกย่อ แปลงเป็น WebP และหมุนถูกทิศ
- รูปที่มี EXIF orientation แบบหมุน 90 องศา → ต้องแสดงถูกทิศหลังบีบอัด
- รูป HEIC จาก iPhone → ต้องแปลงได้
- PNG พื้นหลังโปร่งใส → ต้องคงความโปร่งใส
- รูปเล็กกว่า 2000px → ต้องไม่ถูกขยาย
- PDF แบบสแกน → ต้องเล็กลงชัดเจน
- PDF ที่เป็นข้อความล้วน → ถ้าบีบไม่ลง ต้องเก็บไฟล์เดิม
- PDF ที่เสียหายหรือมีรหัสผ่าน → ต้องอัปโหลดสำเร็จโดยเก็บไฟล์เดิม
- ไฟล์ DOCX และ XLSX → ต้องเก็บตามเดิมและเปิดได้
- ไฟล์ .exe ที่เปลี่ยนนามสกุลเป็น .jpg → ต้องถูกปฏิเสธ
- ไฟล์ใหญ่เกินกำหนด → ต้องถูกปฏิเสธพร้อมข้อความภาษาไทย
- ชื่อไฟล์ภาษาไทยและชื่อที่มีอักขระพิเศษ → ต้องบันทึกและดาวน์โหลดได้ถูกต้อง
- ลบรายการ → ไฟล์จริงต้องถูกลบด้วย

หลังจากนั้น ให้ทดสอบจริงผ่านหน้าเว็บอย่างน้อยหนึ่งจุดในทุกโมดูลที่มีการอัปโหลด

## 9. สคริปต์บีบอัดไฟล์เก่า

- เขียนสคริปต์บีบอัดไฟล์ที่อัปโหลดไว้แล้วในทุกโมดูล ให้ได้ผลเหมือนไฟล์ใหม่
- ต้องมีโหมด **dry-run** ที่แสดงเพียงว่าจะบีบอัดไฟล์ไหน และคาดว่าจะประหยัดพื้นที่ได้เท่าไหร่ โดยไม่แก้อะไรจริง
- ต้องอัปเดต path และข้อมูลในฐานข้อมูลให้ตรงกับไฟล์ใหม่
- ต้องรันซ้ำได้อย่างปลอดภัย โดยข้ามไฟล์ที่บีบอัดแล้ว
- ถ้าหยุดกลางคัน ต้องรันต่อได้
- **ห้ามรันสคริปต์นี้กับข้อมูลจริงเอง** ให้แจ้งฉันพร้อมผลจาก dry-run แล้วรอให้ฉันสั่ง
- แนะนำให้สำรองข้อมูลก่อนรันจริง

## 10. บันทึกกฎถาวรลง CLAUDE.md

เพิ่มหัวข้อด้านล่างนี้ลงใน CLAUDE.md ที่ root ของโปรเจกต์ (ถ้ายังไม่มีไฟล์ให้สร้างใหม่) และแทน `<...>` ด้วยค่าจริง

```markdown
## กฎการอัปโหลดรูปและไฟล์ (บังคับใช้กับทุกส่วนของเว็บ)

ระบบต้องเก็บข้อมูล 10 ปี และพื้นที่ดิสก์มีจำกัด ทุกไฟล์จึงต้องถูกบีบอัดก่อนเก็บ

- ทุกการอัปโหลดในทุกโมดูล ทั้งของเดิมและฟีเจอร์ใหม่ ต้องใช้ upload service กลางที่ `<path>` เท่านั้น
- ห้ามเขียนโค้ดบันทึกไฟล์เองในโมดูลใดๆ
- รูปทุกรูป: หมุนตาม EXIF → ลบ metadata → ย่อด้านยาวไม่เกิน 2000px → แปลงเป็น WebP quality 80 → สร้างรูปย่อ 400px
- PDF ทุกไฟล์: บีบอัดด้วย Ghostscript (~150dpi) ถ้าไม่เล็กลงให้เก็บไฟล์เดิม
- DOCX/XLSX/PPTX: ไม่บีบซ้ำ แต่ต้องจำกัดขนาด
- ต้องมี whitelist ชนิดไฟล์และตรวจจากเนื้อไฟล์จริงทุกครั้ง
- ต้องจำกัดขนาดไฟล์ทุกครั้ง (ค่าเริ่มต้นอยู่ที่ `<ไฟล์ config>`)
- ไฟล์ทุกไฟล์ต้องบันทึกในตาราง `<ชื่อตาราง>` พร้อมขนาดก่อนและหลังบีบอัด
- เมื่อลบรายการ ต้องลบไฟล์จริงด้วย
- เมื่อสร้างหรือแก้ฟีเจอร์ใดที่มีการอัปโหลด ให้ตรวจทุกครั้งว่าใช้ service กลางและทำตามกฎนี้ครบ
- ถ้าต้องการยกเว้นกฎ เช่น เก็บรูปความละเอียดสูง รับวิดีโอ หรือรับ zip ให้ถามเจ้าของโปรเจกต์ก่อน
```

## 11. รายงานผลเมื่อเสร็จ

สรุปให้ฉันดูว่า
1. สร้างหรือแก้ไฟล์อะไรไปบ้าง
2. จุดอัปโหลดทั้งหมดที่แก้ให้ใช้ service กลางแล้ว (เทียบกับตารางในขั้นที่ 1 ว่าครบทุกจุด)
3. ผลทดสอบ พร้อมตารางว่าไฟล์แต่ละแบบลดขนาดได้กี่เปอร์เซ็นต์
4. ผล dry-run ของสคริปต์ไฟล์เก่า (ถ้ามีไฟล์เก่า)
5. สิ่งที่ต้องติดตั้งเพิ่ม หรือต้องทำตอน deploy (เช่น rebuild Docker image)
6. ข้อที่ยังค้างหรือต้องให้ฉันตัดสินใจ

## 12. สิ่งที่ห้ามทำ

- ห้ามเริ่มเขียนโค้ดก่อนที่ฉันจะอนุมัติแผนในขั้นที่ 2
- ห้ามลบหรือเขียนทับไฟล์ที่ผู้ใช้อัปโหลดไว้แล้ว โดยไม่ผ่านสคริปต์และการอนุมัติจากฉัน
- ห้ามบีบอัดจนรูปเอกสารอ่านไม่ออก
- ห้ามให้การบีบอัดที่ล้มเหลวทำให้ผู้ใช้อัปโหลดไม่ได้ (ยกเว้นไฟล์ผิดชนิดหรือใหญ่เกิน)
- ห้าม hardcode ค่าตั้งต้น
- ห้ามข้ามโมดูลใดโมดูลหนึ่ง ต้องครบทุกจุดที่มีการอัปโหลด
